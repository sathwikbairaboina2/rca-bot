# rca-bot v0.1: spec

Date: 2026-10-04 · Author: Claude (Opus lead) for Sathwik · Status: approved by the session brief (autopilot, so there was no brainstorming round; decisions are recorded as ADRs in `docs/adr/`)

Design source: `../docs/devdocs/rca-bot.md` (the full design). Portfolio bar: `../docs/superpowers/specs/2026-10-03-project-shortlist.md`. This spec cuts the design down to what v0.1 can build **and measure** on this machine. The machine has no AWS account, no LocalStack token, and Ollama running on the CPU.

## Why

On-call engineers on serverless AWS stacks spend the first ten minutes of an incident running the same Logs Insights queries. rca-bot does that triage when an alarm fires and posts a short summary where every claim is cited.

The repo backs up the profile thesis: **the model proposes, the deterministic core disposes.** The model picks queries from a fixed catalog and drafts hypotheses. Deterministic code then decides:
- which queries run, and how big they may be;
- whether every citation really exists, character for character, in the stored results;
- how confident the post is;
- what gets posted.

It never takes a remediation action.

## Scope (v0.1)

1. **Core (`src/core/`), pure TypeScript, no I/O**
   - **Types and taxonomy.** The 8 fixed categories from the design.
   - **Logs Insights subset (`core/insights/`).** A lexer, parser and evaluator for `fields`, `filter`, `stats` (count, sum, avg, min, max, pct) `by`, `sort` and `limit`. Filter expressions support `and`, `or`, `not`, comparisons, `like "substring"`, `in [...]` and `ispresent()`. This is the "fixture mode" query engine (ADR 0002). Every catalog template must parse with it.
   - **Query catalog (`core/catalog.ts`).** 8 templates. Parameters are typed: log groups come from an allowlist, and `filterValue` must match `^[A-Za-z0-9_.:/ -]{1,80}$`, rendered as a quoted literal. The time window is clamped to at most 60 minutes inside the incident window (I2, I3).
   - **Evidence verifier (`core/verifyEvidence.ts`).** It applies strict citation checks (I1, ADR 0003).
   - **Confidence (`core/confidence.ts`).** A deterministic band (I9).
   - **Redaction and truncation (`core/redact.ts`).** It masks emails and card-like numbers and caps the rows sent to the model (I12).
2. **Demo service and chaos (`src/demo/`, `src/chaos/`, `scenarios/`)**
   - The `orders` and `payments` handler logic, with fault hooks driven by an SSM-style flag. The flag carries `until`, and expired flags are ignored (I7).
   - 5 labelled scenarios: `ddb-throttle-40`, `payments-5xx-50`, `payments-timeout-30`, `bad-deploy-v18` and `cold-start-storm`.
   - Chaos start, stop and revert-expired logic behind ports. The target must be tagged `chaos:allowed=true` (I8). Durations are capped at 1800 s.
3. **Simulator (`src/sim/`).** It runs the real demo handler code over simulated time with a seeded RNG. The output is:
   - structured JSON logs, plus Lambda platform `REPORT` and timeout lines;
   - per-minute metrics and alarm evaluation (3 breaching 1-minute periods);
   - the deploy timeline, which includes a benign red-herring deploy;
   - the ground-truth label.

   Different seeds give different repeats.
4. **Investigation steps (`src/steps/`) and pipeline (`src/pipeline/investigate.ts`).** The same step functions run inside the Lambda handlers and in-process for `demo` and `eval`. The steps are:
   - `dedupeAndBudget`: grouping, cooldown, query budget and daily token cap (I3, I4, I5);
   - `gatherContext`;
   - `planQueries`: the model picks from the catalog, validated, capped and retried once, with a deterministic default plan as the fallback;
   - `runQueries`;
   - `hypothesize`: schema-validated, retried once, then inconclusive (I10);
   - `verify`;
   - `postSlack`.
5. **Ports and adapters**
   - The incident store, with a memory version and a DynamoDB single-table version.
   - The query runner, with a fixture evaluator and a CloudWatch Logs version (`StartQuery`/`GetQueryResults`, timeout, truncation, `bytesScanned`).
   - The results store, with a memory version and S3.
   - The model: Ollama (`/api/chat` with a JSON-schema `format`), Bedrock (Converse with forced tool use), scripted (tests), heuristic (a rule-based baseline) and fabricator (wraps another model and corrupts citations, for the verifier bench).
   - Slack: a Block Kit renderer, plus webhook, sink-HTTP and file posters.
6. **CLI `rca`**
   - `demo <scenario>`
   - `eval run`
   - `eval fabrication`
   - `catalog lint`
   - `chaos list|start|stop`
   - `incident show`
7. **Slack sink (`docker/slack-sink/`).** A tiny Node server in Docker (`rca-bot-slack-sink`, host port 5350). It records posts and renders them as HTML cards.
8. **AWS infrastructure (`infra/`, CDK v2).** The infrastructure is only synthesized; it is never deployed in v0.1.
   - `RcaDemoService`: REST API, the orders and payments Lambdas, the Orders table, and the `orders-5xx-rate` and `orders-p99-latency` alarms. The resources are tagged `chaos:allowed=true`.
   - `RcaChaos`: the chaos Lambda, the SSM flag parameter, and a `rate(1 minute)` revert rule. IAM conditions are on the tag.
   - `RcaInvestigator`: an EventBridge alarm rule, then Step Functions Standard (`DedupeBudget → Choice → GatherContext → PlanQueries → Map(RunQuery) → Hypothesize → Verify → PostSlack`). It also has the Incidents table, the artifacts bucket, and read access to a Slack webhook SSM SecureString parameter that is created outside the stack. IAM is least privilege (I6).
   - Lambda code is prebundled with esbuild into `dist/lambda/<name>/index.mjs`.
9. **Tests and CI.** Vitest unit, property (fast-check) and CDK-assertion tests. There is one LocalStack contract test, gated by `RCA_LOCALSTACK=1`. It skips cleanly without the env var.
10. **Docs.** README (headline number, the 30-second demo, a mermaid diagram, the invariant table), `docs/DEVDOCS.md`, `docs/handoff.md` and `bench/README.md`.

## Out of scope (v0.1)

- **Deploying to LocalStack or AWS.** There is no token, and the CDK asset step is paid on LocalStack (ADR 0007).
- **Slack interactivity.** Feedback buttons are rendered, but signature verification (I11) and the feedback handler are v0.2.
- **The deploy timeline from real AWS APIs.** `gatherContext` on AWS reads only the alarm and `GetMetricData` in v0.1. The simulator provides deploys locally.
- **USD pricing.** Budgets are in tokens (ADR 0006).
- **Powertools.** The demo service emits the same JSON field shape itself (ADR 0004).
- **Automated remediation.** This is permanent, not just for v0.1.

## Headline benchmark definitions

- **`rca eval run --model <m> --scenarios all --repeat R`** runs all 5 scenarios `R` times, with seed = `1000 + repeat index`. For each run it:
  1. simulates the scenario;
  2. takes the expected alarm event;
  3. runs the full pipeline with the fixture query runner and memory stores;
  4. scores the result.

  Metrics per run:
  - **top-1:** the first posted hypothesis has the expected category. An inconclusive result counts as wrong.
  - **top-2:** the expected category is in the first two posted hypotheses.
  - **inconclusive:** nothing survived verification.
  - **unverified posted:** the harness re-verifies every posted hypothesis against the stored results with a fresh call to `verifyEvidence`, and counts the failures. The target is 0.
  - Also recorded: `dropped` count, model calls, input and output tokens, queries run, and wall-clock ms.

  Results are written to `bench/results/eval-<model-slug>.json`, rewritten after every run so a partial run keeps its data. The summary covers top-1, top-2 and the inconclusive rate (overall and per scenario), the unverified-posted total, the median latency and the total tokens. The environment is labelled `local-fixture` (simulator plus fixture Logs Insights engine), never "deployed".
- **`rca eval fabrication --repeat R`** wraps the heuristic model with the fabricator. The fabricator keeps one honest hypothesis per run and adds fabricated ones, using 4 mutation kinds:
  - a single-character change to a quoted value;
  - a wrong row;
  - an unknown queryId;
  - an invented field.

  The bench measures `fabricatedBlocked / fabricatedInjected` and `honestKept / honestInjected`, and writes `bench/results/fabrication.json`.
- **Models used for the README:** `heuristic` (deterministic baseline, always run) and `ollama:qwen3.8:27b` (run in the background, with `--repeat 3` if it finishes in time, otherwise the measured `--repeat 1`). The README states `n` and the model for every number.
